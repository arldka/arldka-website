My homelab is two small machines in France. I was not there: I was on the other side of the world, behind a heavily restricted network. The only way in was SSH over Tailscale, which doesn't work well from there on its own, so I had to put some v2ray shenanigans on top of it just to reach my own machines. And I wanted to replace the operating system underneath a running Kubernetes cluster.

This is how that went, and why I wanted to do it in the first place.

## Where I started

The cluster was k3s on Debian 13, two nodes: one control plane and one worker. Flux reconciled everything from Git, storage was a mix of `local-path` and an NFS CSI driver pointing at my NAS, and both apps and kube-apiserver were exposed through the Tailscale operator.

It worked. But I was not happy with the upkeep:

- **Upgrades.** I used Rancher's system-upgrade-controller to auto-upgrade k3s. It's one more controller to keep alive, with its own plans and its own failure modes, and the OS under it (Debian) still needed separate attention.
- **The provisioner.** `local-path` is fine until you remember that a volume is a directory on one specific node. Two of my claims still used it. Everything else used NFS CSI PVCs even for RWO workloads, causing unpleasant noise pollution where the servers run due to HDD activity on the NAS. Furthermore, it meant that all of the high-speed storage of my hardware was by and large left unused.
- **Configuration.** k3s is configured by a mix of flags, `/etc/rancher` files and whatever was on the host. The state of the machine wasn't something I could read in a repository.

There was mainly one thing that originally drove me to choosing k3s: with a single control plane, **kine on SQLite** instead of etcd for its supposedly lower overhead. 

## The etcd worry, really that hungry?

Talos runs a standard etcd. So before moving, I wanted to know what I was giving up.

The k3s team publishes [resource profiling](https://docs.k3s.io/reference/resource-profiling) for exactly this comparison. For a single-node server running a simple workload, the minimum memory they measured was about 1596 MB with SQLite and 1606 MB with embedded etcd on an Intel machine. That's a 10 MB difference. The gap only grows on a Pi 4 with an agent attached, to roughly 200 MB.

Under load it can even go the other way. kine translates etcd API calls into SQL, and a [third-party vCluster benchmark](https://vcluster.com/pro/docs/load-testing/results) found k3s with SQLite used more CPU than the etcd-based distributions under heavy API traffic, and could time out or get throttled.

What etcd is really dependent on is the disk performance and latency. It fsyncs every write to its log and wants a p99 fsync latency under about 10 ms ([Red Hat's etcd guidance](https://docs.redhat.com/en/documentation/openshift_container_platform/4.19/html/etcd/etcd-practices) says the same). That's what kills SD cards and cheap SSDs. My control plane runs on an NVMe drive.

And a single control plane has no quorum either way, so backups are still required.

Here's what it actually costs on my cluster:

etcd on talos-1 uses **1334 MB** of memory, with a p99 WAL fsync of **1.82 ms**. That's well under the 10 ms budget.

For my specific use case, it appears that there is no real reason to favor kine/SQLite or etcd.

You might have noticed that the roles of my machines have swapped. In the k3s cluster the NUC was the control plane and the ThinkPad was the worker. In the new cluster the ThinkPad is the control plane. This switch turned out to have a very useful side effect that will be explained later on in the post. 

## The plan: blue-green one machine at a time 

I couldn't take the whole cluster down, because a cluster that is down also takes my only way in with it. So I built the new cluster next to the old one:

1. **Consolidate.** Move every workload onto the original k3s control plane (the NUC) and drain the k3s worker (the ThinkPad).
2. **Replace the worker.** Turn the freed ThinkPad into the new Talos control plane, a brand new single-node cluster.
3. **Reinstall the workloads.** Point Flux at the new cluster and let it bring everything back. Most of my stateful data already lived on the NAS behind the NFS CSI driver, so the new cluster just mounts the same data. No restore from backup was needed for those volumes.
4. **Retire k3s.** Drain and stop k3s on the NUC, convert it to Talos, and join it to the new cluster as a worker.

At every step there was a machine still running and reachable over Tailscale. The riskiest moment was the conversion itself, when a machine goes from "Debian I can SSH into" to "Talos, which has no SSH at all".

Using the ThinkPad in my current setup means taking advantage of the battery that is kept at 50% charge so it gives me a machine from which I can send a magic packet to wake up the rest of the infrastructure as I don't currently have a UPS running.

## Designing for no physical access

A Talos node has no SSH and no shell. If it comes up without a network, I can't fix it from where I am. So everything that matters had to be decided before the machine rebooted.

### Tailscale from the first boot

I baked the Tailscale extension into the image with an [Image Factory](https://factory.talos.dev) schematic, so the node joins my tailnet the moment it boots. The Longhorn and NFS needs come from the other extensions:

```yaml
customization:
  systemExtensions:
    officialExtensions:
      - siderolabs/iscsi-tools
      - siderolabs/util-linux-tools
      - siderolabs/nfs-utils
      - siderolabs/tailscale
      - siderolabs/realtek-firmware
      - siderolabs/amd-ucode      # intel-ucode on the NUC
```

The Tailscale auth key is passed as an environment variable to the extension service:

```yaml
apiVersion: v1alpha1
kind: ExtensionServiceConfig
name: tailscale
environment:
  - TS_AUTHKEY={{ .Node.Data.tsKey }}
```

### A static address and an explicit LAN subnet

I don't want Talos picking the wrong interface or a Tailscale address as its node IP. Static addressing and a pinned subnet take that choice away:

```yaml
machine:
  certSANs:
    - talos-1.<tailnet>
  network:
    interfaces:
      - deviceSelector:
          hardwareAddr: "<mac-address>"
        dhcp: false
        addresses:
          - 192.168.1.52/24
        routes:
          - network: 0.0.0.0/0
            gateway: 192.168.1.254
---
apiVersion: v1alpha1
kind: KubeNodeConfig
nodeIP:
  validSubnets:
    - 192.168.1.0/24
```

The MagicDNS name goes into the API server certificate too, so `kubectl` over the tailnet validates:

```yaml
apiVersion: v1alpha1
kind: KubeAPIServerConfig
certExtraSANs:
  - 192.168.1.52
  - talos-1.<tailnet>
```

### Picking the install disk safely

The ThinkPad has more than one disk and both are of the same capacity. Installing on the wrong one could break everything, so I select the disk by serial number rather than by device name, which can change:

```yaml
apiVersion: v1alpha1
kind: UnattendedInstallConfig
provisioning:
  diskSelector:
    match: disk.serial == "<disk-serial>"
  wipe: true
```

The new setup will also be using the second disk. A user volume claims any non-system disk of 100 GB or more for Longhorn:

```yaml
apiVersion: v1alpha1
kind: UserVolumeConfig
name: longhorn
provisioning:
  diskSelector: { match: "!system_disk" }
  minSize: 100GB
filesystem: { type: xfs }
```

## Installing Talos next to Debian with kexec

Using kexec makes things simpler: from the running Debian system, load the Talos kernel and initramfs and jump straight into them without going through the firmware. If the machine doesn't come back, a power cycle returns to the old OS, because nothing has been written to disk yet. Only once the node is up in Talos' maintenance mode, reachable over the LAN, do I apply a machine config and let Talos install itself to the disk I chose.

I did it in two stages. First, install Talos on the disk that was unused and prove that it works, while Debian stays bootable. Then make Talos the default boot entry, and only after that wipe Debian.

### Fetch the right image for the right node

Each node has its own Image Factory schematic, because the two machines need different extensions. The ThinkPad is AMD and needs `amd-ucode`; the NUC is Intel and needs `intel-ucode`. Don't mix them up: Intel microcode on an AMD machine can freeze the node completely, and a frozen node was unrecoverable in my situation.

On the Debian box, download the kernel and the initramfs for that node's schematic:

```bash
mkdir -p /boot/talos
cd /boot/talos
curl -LO https://factory.talos.dev/image/<SCHEMATIC_ID>/<TALOS_VERSION>/kernel-amd64
curl -LO https://factory.talos.dev/image/<SCHEMATIC_ID>/<TALOS_VERSION>/initramfs-amd64.xz
```

### Jump into Talos

Load them with kexec, flush the disks, and execute:

```bash
kexec -l kernel-amd64 --initrd=initramfs-amd64.xz \
  --command-line="talos.platform=metal console=tty0 init_on_alloc=1 slab_nomerge pti=on ip=<IP>::<GW>:<NETMASK>:talos-1:<IFACE>:off"
sync
kexec -e
```

The `ip=` argument gives the node a static address in maintenance mode, in the form `client::gateway:netmask:hostname:interface:autoconf`. Without a machine config the Tailscale extension isn't running yet, so at this point the node is reachable only on the LAN.

### Look before you configure

From a terminal that can reach the node's LAN address, ask Talos what it sees:

```bash
talosctl -n <IP> get disks --insecure
talosctl -n <IP> get links --insecure
```

Check the config patch against what these commands return: the disk serial, the interface name, the MAC address.

One thing I left out on purpose: the Longhorn claim. Debian was still running on the other disk, and a claim for "any non-system disk" would have grabbed it. The claim only goes in once Talos is completely set up.

### Generate, validate, apply

Create the cluster secrets and the machine config. Back up `secrets.yaml` somewhere safe, because you can't recreate the cluster identity without it:

```bash
talosctl gen secrets -o secrets.yaml
talosctl gen config homelab https://<LAN_IP>:6443 \
  --with-secrets secrets.yaml --config-patch @patch.yaml -o _out
```

Validate it before it goes anywhere near the node:

```bash
talosctl validate --config _out/controlplane.yaml --mode metal
```

If that's clean, apply it. This is the moment Talos installs itself, on the disk selected by serial:

```bash
talosctl apply-config --insecure -n <IP> -f _out/controlplane.yaml
```

### Bootstrap

Point `talosctl` at the new node and bring the cluster up:

```bash
export TALOSCONFIG=$PWD/_out/talosconfig
talosctl config endpoint <IP>; talosctl config node <IP>
talosctl bootstrap
talosctl kubeconfig
```

### Back to Debian, on purpose

In the testing and validating phase, we really want to switch from Debian and Talos booting back into one and the other to both validate the installation and also keep a way to start everything all over again. 

```bash
talosctl reboot --mode powercycle
```

The `powercycle` mode skips kexec and goes through the firmware. The boot order was unchanged, so the machine came back as Debian. Talos was installed on what used to be the unused disk, and Debian had never been touched.

### Making Talos boot on its own

The following steps then explain how to boot into Talos, validate the setup and then make it the default. Both steps use plain UEFI boot entries, managed from Debian with `efibootmgr`.

When Talos installed itself on the spare disk, it also registered its own boot entry in the firmware. List the entries and find it:

```bash
efibootmgr -v
```

Then boot into it once, and only once:

```bash
efibootmgr --bootnext <entry number>
systemctl reboot
```

`BootNext` is one-shot. If Talos hadn't come up, the next boot would have gone back to Debian by itself. It did come up, I checked it from the outside, and I power-cycled again, which put Debian back because the `BootNext` had been used up.

Only then did I make Talos the default, still from Debian, and rebooted:

```bash
efibootmgr --bootorder <talos entry>,<debian entry>
systemctl reboot
```

The node came up as Talos with Debian still on its disk as a fallback. Only after Talos had proven stable and reachable did I wipe the Debian disk.

#### Why not GRUB?

The obvious way to chain-load Talos from Debian is a GRUB entry. GRUB lives on the Debian disk, and that disk was going to be wiped. The moment it was, the boot menu, the entry and the bootloader would all disappear, and the machine would have nothing left to boot from.

The UEFI entry has no such problem. It lives in the firmware's own storage, and it points to the boot partition Talos created on its own disk. Wiping Debian doesn't touch either of them.

## Cilium instead of Flannel and kube-proxy

I wanted Cilium, so I deleted Talos' default Flannel and turned off kube-proxy through two small config documents:

```yaml
apiVersion: v1alpha1
kind: KubeFlannelCNIConfig
$patch: delete
---
apiVersion: v1alpha1
kind: KubeProxyConfig
enabled: false
```

Cilium itself is installed by Flux. Two values matter on Talos with Tailscale:

```yaml
kubeProxyReplacement: true
k8sServiceHost: localhost   # Talos' KubePrism endpoint
k8sServicePort: 7445
devices: ["eth+", "en+"]    # physical NICs only, keeps Cilium off tailscale0
socketLB:
  hostNamespaceOnly: true   # needed for the Tailscale operator
```

Pinning `devices` to physical interfaces keeps Cilium from trying to manage `tailscale0`, which is the interface my own access depends on.

## Making upgrades easy

The reason I left k3s is now one line in a file. Machine configuration lives in the repository, managed with [topf](https://github.com/postfinance/topf), with secrets encrypted by SOPS and age. Upgrading Talos or Kubernetes means bumping a version in `topf.yaml`:

```yaml
kubernetesVersion: 1.37.1
talosVersion: 1.14.5
```

and running `topf upgrade`. Renovate opens the pull requests for everything else (Cilium, Flux, the Tailscale operator).

The issue with a single control plane: the API is down while `talos-1` reboots, and if the Tailscale extension doesn't come back I'm locked out. Adding other devices to run a highly available control plane will be one of the most important next steps. 

## Mistakes along the way

- **Config documents changed shape.** Talos is moving from the single `v1alpha1` machine config to separate documents (`UnattendedInstallConfig`, `KubeNodeConfig`, `HostnameConfig`, ...). My patches went through three iterations before the validator and the node agreed.
- **I forgot disk encryption.** I never set up LUKS on the Talos nodes. Talos can encrypt its system partitions, but it's a decision you make at install time, and I only thought of it afterwards. For now I'm planning to encrypt the sensitive volumes through Longhorn instead. That protects the data in those PVCs, but it doesn't replace encrypting the node disks themselves: the machine secrets, etcd and everything else on the system partitions stay readable to anyone who holds the disk.
- **I forgot Secure Boot.** Same story, and it's still on my list. Talos supports it with signed images, and it's also what makes tying disk encryption to the TPM worthwhile. Doing it later means enrolling keys in the firmware of machines I can't touch, so it will need the same care as the original migration.

## Was it worth it?

As a learning opportunity, yes! Was the move justified or necessary in my case? Not quite. The main point of running a homelab for me is still having fun and overengineering things is good enough reason for me. Now the whole machine is in Git: the OS image, the network settings, the disk layout, the extensions. Once the migration is done, everything that remains is fully GitOps driven and deterministic. The kine/SQLite advantage was based on blind preconceptions and turned out small in practice

What I'd tell someone considering the same move without physical access: think about your way back in (Tailscale in the image), select disks by serial if needed, pin the network, and make sure at every step that one machine is still alive and reachable. I definitely didn't feel confident during slow reboots!

Honestly, the migration wasn't driven by actual needs at all. It came from new things I wanted to do with the homelab, and from a slow build-up of small annoyances with the old setup. It was also partly procrastination: I replaced the operating system under a running cluster instead of starting on what I had meant to build in the first place.

The configuration is public if you want to see how it all fits together. It will be updated as everything evolves: [arldka/kubernetes-homelab](https://gitlab.com/arldka/kubernetes-homelab).
